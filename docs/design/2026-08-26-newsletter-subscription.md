# 뉴스레터 구독 설계 승인

## 배경과 목표

MAGMA 회사소개 사이트에 뉴스레터 구독 흐름을 추가하기 위한 설계 결정이다. 목표는 방문자가 이메일 하나만으로 구독 의사를 남길 수 있게 하되, 구현 초기 단계에서는 보안·개인정보·운영 안정성을 해치지 않는 범위에서 개발용 저장소에만 기록하는 것이다.

이번 문서는 구현 지시가 아니라 확정된 제품·기술 결정을 남기는 설계 문서다. 실제 공개 전에는 아래 테스트와 공개 조건을 모두 만족해야 한다.

## 확정된 여섯 가지 결정과 선택 이유

### 1. 폼 위치

결정: 홈 화면의 브랜드 소개 섹션 아래, 최신 블로그 섹션 앞에 별도 뉴스레터 섹션을 둔다.

선택 이유:
- 브랜드 소개를 읽은 직후가 MAGMA의 방향성에 공감한 사용자가 다음 행동을 취하기 좋은 지점이다.
- 최신 블로그 섹션 앞에 배치하면 콘텐츠 탐색 전에 구독 행동을 명확히 제안할 수 있다.
- 별도 섹션으로 분리하면 히어로·브랜드 소개·블로그 목록의 역할을 훼손하지 않고, 이후 디자인이나 카피를 독립적으로 조정할 수 있다.

### 2. 받을 정보

결정: 이메일 하나만 받는다. 이름과 태그는 받지 않는다.

선택 이유:
- 가입 장벽을 낮추고 전환 흐름을 단순하게 유지한다.
- 초기 운영 단계에서 필요하지 않은 개인정보를 수집하지 않아 보안·보관 부담을 줄인다.
- 태그나 세그먼트는 실제 발송 전략이 정해진 뒤 서버 측 데이터 모델을 확장해도 늦지 않다.

### 3. 오류·중복 처리

결정: 이메일 입력값은 앞뒤 공백을 제거하고 영문을 소문자로 변환한다. 브라우저와 서버 양쪽에서 형식 검증을 수행한다. 신규 주소와 이미 등록된 주소에는 같은 성공 메시지를 반환해 등록 여부가 드러나지 않게 한다.

선택 이유:
- 공백 제거와 소문자 변환으로 같은 주소가 다른 문자열로 저장되는 문제를 줄인다.
- 브라우저 검증은 빠른 피드백을 제공하고, 서버 검증은 우회 요청과 자동화 요청을 방어한다.
- 중복 여부를 응답으로 구분하지 않으면 특정 이메일이 이미 등록됐는지 외부에서 추측하기 어렵다.

### 4. 화면 동작

결정: 제출 중에는 버튼을 비활성화해 중복 클릭을 막는다. 성공 시 인라인 감사 메시지를 표시한다. 실패 시 오류 메시지를 표시하되 입력값은 보존한다.

선택 이유:
- 버튼 비활성화는 같은 요청이 짧은 시간에 여러 번 발송되는 일을 줄인다.
- 인라인 감사 메시지는 페이지 이동 없이 사용자가 결과를 즉시 확인하게 한다.
- 실패 시 입력값을 보존하면 사용자가 오타나 네트워크 오류를 수정해 다시 제출하기 쉽다.

### 5. 저장 방식

결정: 저장 담당 코드를 `SubscriberStore` 같은 인터페이스로 분리한다. 현재 구현체는 개발용 로컬 파일(JSONL)을 사용한다. 나중에 DB나 외부 이메일 서비스로 교체할 때 폼과 API 계약은 건드리지 않는다.

선택 이유:
- 폼과 API 라우트는 구독 요청의 입출력 계약에 집중하고, 저장소 교체는 인터페이스 뒤로 숨길 수 있다.
- 개발 단계에서는 로컬 JSONL이 설정 비용이 낮고 diff·검수·테스트가 쉽다.
- 실제 배포 저장소가 DB, CRM, 이메일 마케팅 서비스 중 무엇이 되더라도 교체 범위를 저장 구현체로 제한할 수 있다.

### 6. 테스트·공개 조건

결정: Vitest를 도입해 정규화·검증·중복 로직을 단위 테스트한다. 폼 동작은 브라우저로 육안 확인한다. 공개 조건은 잘못된 이메일 미저장, 정규화 동작, 재제출해도 1건, 중복 클릭 차단, 성공·실패 메시지 표시, lint·build 통과, 이메일이 클라이언트 번들이나 로그에 노출되지 않음이다.

선택 이유:
- 정규화·검증·중복 로직은 작고 결정적인 규칙이므로 단위 테스트로 회귀를 막기 좋다.
- 폼의 제출 중 상태, 메시지 표시, 입력값 보존은 실제 브라우저 상호작용으로 확인해야 신뢰할 수 있다.
- 공개 조건을 명시하면 구현 완료와 배포 가능 상태를 혼동하지 않을 수 있다.

## 저장 방법 3안 비교

| 안 | 저장 방법 | 장점 | 단점 | 적합한 시점 |
| --- | --- | --- | --- | --- |
| 1안 | API 라우트에서 로컬 JSONL 파일에 직접 저장 | 구현이 가장 빠르고 의존성이 없다 | API와 저장 세부사항이 강하게 결합되어 DB나 외부 서비스로 교체할 때 API 수정 가능성이 크다 | 임시 스파이크나 폐기 예정 실험 |
| 2안 | API 라우트에서 DB 또는 외부 이메일 서비스에 직접 저장 | 실제 운영 저장소와 바로 연결할 수 있다 | 초기 설정·비밀값·네트워크 실패 처리가 필요하고, 공개 전 검증 범위가 커진다 | 저장소와 운영 계정이 이미 확정된 뒤 |
| 3안 | `SubscriberStore` 인터페이스 + 개발용 로컬 JSONL 구현체 | 개발 중 검증이 쉽고, 나중에 저장소를 교체해도 폼과 API 계약을 유지할 수 있다 | 인터페이스와 구현체 분리 구조를 먼저 잡아야 한다 | 현재 단계 |

선택: 3안, 즉 ⑤안을 선택한다.

선택 이유:
- 현재는 구독 경험과 서버 계약을 검증하는 단계이며, 운영 저장소가 확정되지 않았다.
- 로컬 JSONL은 개발·테스트 중 실제 저장 결과를 확인하기 쉽다.
- 저장소 교체 가능성을 설계에 포함해 두면 이후 DB나 외부 서비스 도입 시 변경 범위와 회귀 위험을 줄일 수 있다.

## 데이터 흐름

1. 구독 폼
   - 사용자가 홈 화면 뉴스레터 섹션에서 이메일을 입력한다.
   - 브라우저에서 앞뒤 공백 제거와 형식 검증을 수행한다.
   - 제출 중에는 버튼을 비활성화한다.

2. API 라우트
   - 요청 본문에서 이메일을 읽는다.
   - 서버에서 다시 앞뒤 공백 제거와 영문 소문자 변환을 수행한다.
   - 서버에서 이메일 형식을 검증한다.
   - 유효하지 않은 이메일은 저장하지 않고 오류 응답을 반환한다.

3. `SubscriberStore`
   - API 라우트는 저장 구현체의 세부사항을 알지 않고 인터페이스를 통해 저장을 요청한다.
   - 저장 구현체는 정규화된 이메일 기준으로 중복 여부를 판단한다.
   - 신규 주소와 중복 주소 모두 API에는 같은 성공 결과를 돌려준다.

4. 파일
   - 개발용 구현체는 정규화된 이메일을 로컬 JSONL 파일에 저장한다.
   - 이미 저장된 이메일이면 새 줄을 추가하지 않는다.
   - 클라이언트 번들이나 서버 로그에 이메일 원문을 노출하지 않는다.

## 오류 처리 규칙

- 빈 값 또는 형식이 잘못된 이메일은 저장하지 않는다.
- 브라우저 검증 실패 시 API 요청을 보내지 않고 인라인 오류 메시지를 표시한다.
- 서버 검증 실패 시 오류 응답을 반환하고, 화면은 오류 메시지를 표시하되 입력값을 보존한다.
- 저장 중 예외가 발생하면 일반 실패 메시지를 표시하고 입력값을 보존한다.
- 신규 구독과 중복 구독은 같은 성공 메시지를 사용한다.
- 중복 여부, 저장 파일 경로, 내부 예외 상세, 등록된 이메일 목록은 클라이언트에 노출하지 않는다.
- 서버 로그에는 이메일 주소를 기록하지 않는다. 필요하면 요청 성공·실패 상태와 익명화된 원인만 기록한다.

## 테스트 목록

### 단위 테스트: Vitest

- 이메일 앞뒤 공백 제거.
- 이메일 영문 소문자 변환.
- 유효한 이메일 형식 통과.
- 잘못된 이메일 형식 거부.
- 잘못된 이메일은 저장하지 않음.
- 같은 이메일을 대소문자나 공백이 다른 형태로 다시 제출해도 저장 결과는 1건.
- 신규 주소와 중복 주소가 같은 성공 결과를 반환.

### 브라우저 육안 확인

- 뉴스레터 섹션이 홈 화면 브랜드 소개 섹션 아래, 최신 블로그 섹션 앞에 보임.
- 제출 중 버튼이 비활성화되어 중복 클릭이 차단됨.
- 성공 시 인라인 감사 메시지가 표시됨.
- 실패 시 오류 메시지가 표시되고 입력값이 보존됨.
- 잘못된 이메일 입력 시 저장이 발생하지 않음.

### 공개 전 검증

- `npm run lint` 통과.
- `npm run build` 통과.
- 클라이언트 번들에 구독 이메일이 포함되지 않음.
- 서버 로그에 구독 이메일이 출력되지 않음.
- 개발용 JSONL 파일이 운영 배포 산출물이나 공개 저장소에 실수로 포함되지 않음.

## 공개를 미루는 조건

이 설계는 개발용 로컬 JSONL 저장을 전제로 하므로, 이 상태 그대로는 아직 배포하면 안 된다.

공개를 미뤄야 하는 이유:
- 운영 환경에서 로컬 파일 저장은 영속성, 백업, 동시 쓰기, 장애 복구를 보장하기 어렵다.
- Vercel 같은 서버리스 배포 환경에서는 런타임 파일 쓰기가 영구 저장소로 동작하지 않을 수 있다.
- 이메일은 개인정보에 해당하므로 운영 저장소, 접근 권한, 보관 기간, 삭제 요청 처리 방식이 확정되어야 한다.
- 발송 도구나 DB가 확정되기 전에는 실제 뉴스레터 운영 흐름과 수신 동의 관리가 불완전하다.
- 스팸·봇 제출에 대한 최소 방어 정책이 구현·검증되어야 한다.
- 테스트 목록과 공개 전 검증 항목이 모두 통과했다는 실행 근거가 필요하다.

따라서 이 설계의 현재 공개 조건은 “개발 환경에서 동작과 계약을 검증할 수 있음”까지이며, 운영 공개는 영속 저장소와 개인정보 운영 기준을 확정한 뒤 진행한다.
